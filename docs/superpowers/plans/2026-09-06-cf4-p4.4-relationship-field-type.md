# Custom Fields 4.0, Plan 4.4: Record and Relationship as Two Field Types

> **For agentic workers:** REQUIRED SUB-SKILL: sdd-lean, task-by-task. Runs on the package `feat/4.0` branch AFTER plans 3.1, 3.2, 4.1 and 4.2 have landed. Implements the 2026-09-06 amendment recorded in the phase 3 and phase 4 specs. Package quality gate per task, plus the UI rule for every touched screen.

**Goal:** Keep the Record field exactly as users know it (a one-way link with a target entity and an allow-multiple toggle, edited through a plain select) while a new `relationship` field type carries everything the ledger made possible: paired fields, cardinality, symmetry, the configurator, the chip picker. Both types share one storage and one code path underneath.

**Why this plan exists:** the phase 3 spec folded the one-way Record field into the relationship concept as a one-slot definition, and phase 4 then gave every Record field the configurator and chips. The maintainer decided on 2026-09-06 that Record must not change its face: hosts and users read "Record" as the simple link it always was. The ledger stays underneath (no dangling ids, sortable and searchable, one migration path); only the presentation and the configuration split.

**Decisions:**

1. Two field types, one substrate. `record` (key unchanged) and `relationship` (new key) both implement `requiresRelationship()`, both store links in `custom_field_links` through a definition, both read through `LinkReader`, both validate through `CardinalityGuard`.
2. Record keeps its 3.x configuration surface: target entity type (locked after create) and an allow-multiple toggle. The toggle maps to cardinality (`many_to_many` when on, `many_to_one` when off) on a one-slot definition; narrowing from multiple to single asks the keep-first confirmation exactly as a cardinality change does. No pairing, no symmetric toggle, no per-side names. `max_values` is not offered (cardinality has no count cap; note it in the upgrade guide).
3. Record keeps its simple components: the select-based form component, the existing column and entry renderers, the existing filter. Sorting and searching stay enabled (they are storage improvements users asked for, not a face change).
4. Relationship owns the phase 4 UI: the configurator surface, the chip picker with inline steal confirmation, chips in columns and entries, pair connection in the attribute table, the sentence-style creation flow. A Relationship definition may have one or two slots.
5. The migration step keeps producing one-slot definitions for legacy Record fields; their type stays `record`. Converting a Record field into a Relationship field is a definition edit (add a slot) and is out of scope for 4.0.
6. Through-relation tables, option categories, bulk paste, the flavor registry, and every phase 1 to 3 substrate decision are unaffected.

### Task 1: Split the field type

- `src/FieldTypeSystem/Definitions/RecordFieldType.php` keeps key `record`, its label, `requiresRelationship()`, sortable and searchable; its form component is the select-based `RecordSelectInputComponent` in its pre-chip form (restore the select rendering path; keep the map-aware dehydration because a Record field on a single side still needs the confirmed replace when the host sends `['ids' => [...], 'replace' => true]` through the API).
- New `src/FieldTypeSystem/Definitions/RelationshipFieldType.php`, key `relationship`, label and description lang keys, `requiresRelationship()`, sortable, searchable, filterable; form component: the chip picker; column and entry: the chip renderers; filter: the link filter. Register it in `DEFAULT_FIELD_TYPES`, the type picker (icon and description), and the docs field-types page.
- `FieldSchema`/`FieldTypeData`: a capability that distinguishes the two (`supportsPairing()` or similar) so the configurator and the pair connection in the attribute table read the capability, never the key.
- Tests: both types create, read, and clear links through the trait; the type picker lists both; a Record field never shows the configurator; a Relationship field always does.

### Task 2: Record configuration back to its face

- `FieldForm::recordConfiguration()` branches on the capability: for `record`, a target entity select (locked after create) and an allow-multiple toggle; for `relationship`, the configurator (polished) or the stock fieldset (native).
- `ManagesCustomFields::{storeField,updateField,copyRelationship}`: the Record path builds a one-slot `RelationshipDefinitionData` from the two inputs; toggling allow-multiple off on an existing field routes through `UpdateRelationshipDefinition` with the keep-first confirmation; duplicating a Record field copies its one-slot definition.
- `FieldForm::relationshipState()` fills the toggle from the definition's cardinality.
- Tests: create a single and a multiple Record field through the management form and assert the definition shape; toggle multiple off with existing multi-links and assert keep-first; ends locked on edit; the native and polished flavors render the same Record form.

### Task 3: Components by type

- `RecordSelectInputComponent` renders the select (native and polished identical) for `record`; the chip picker is a separate form component class bound to `relationship` (move the picker Alpine partial and the polished picker view under it).
- `RecordColumn`/`RecordColumnView` and `RecordEntry` keep their pre-chip rendering for `record`; the chip renderers become the Relationship column and entry (new classes or a capability branch inside the existing ones, whichever keeps one query shape; say why).
- `RecordFilter` serves both (it filters by linked id either way).
- `RecordChips` stays the single chip builder for the Relationship surfaces.
- Tests: both types through `ListPosts`, `ViewPost`, `EditPost`; query counts unchanged; the steal confirmation only on the Relationship picker; a Record single-side conflict still reports the holder through validation.

### Task 4: Docs, migration, and host notes

- Docs: field-types page gains the Relationship type; the relationships docs page states the two types and when to pick each; the upgrade guide says Record fields are unchanged for users (sorting and searching gained, `max_values` gone), and that Relationship is new.
- The migration step and `custom-fields:upgrade` output name the type they create (`record`) so a host reading the log sees no rename.
- The phase 5 host plan gains a note: chat, REST, MCP, and import detect link fields by definition, never by key, so both types are covered; the Relationship type is described with its pairing and cardinality in the chat schema.
- Verify: full gate on all three drivers; both flavors.
