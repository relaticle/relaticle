# Custom Fields 4.0, Plan 4.1: Relationship UI and Field-Management Polish

> **For agentic workers:** REQUIRED SUB-SKILL: sdd-lean, task-by-task. Runs on the `4.x` branch AFTER Plan 3.1 (substrate); every service this plan renders against (CreateRelationshipDefinition, LinkWriter, LinkReader, the events) exists by then. Package quality gate per task, plus the UI rule: every screen is verified with agent-browser click-throughs (light AND dark, mobile viewport, empty states) before any done claim. Package UI stays themeable; no host styling leaks in.

**Goal:** Implement the phase 4 spec (2026-09-03-cf4-p4-relationship-ux-spec.md), sections 3.1 to 3.4: the relationship creation flow, the record-side experience, the field-management polish pass, and the flavor registry that carries all of it in two presentations over one logic layer.

**Decision context:** the flavor registry was re-examined in the 2026-09-01 architecture review and explicitly KEPT. The accepted cost (15 to 20 percent on UI work, doubled browser CI on critical paths) is bounded by the rule below: logic never forks; only views fork, and only on the four polished surfaces.

### Task 1: Flavor registry foundation

- Config: `ui.flavor` (`polished` default, `native`) plus a per-component override map.
- A view-resolution helper the four custom surfaces render through: polished resolves to the package's custom Blade views, native to stock Filament rendering of the same Livewire classes.
- The four forked surfaces, and ONLY these: relationship configurator, record chips and picker, type-picker grid, attribute table. Everything else uses stock Filament in both flavors.
- Test: unit-level resolution (flavor + override map), and a Livewire render smoke of one surface in each flavor.
- Build this FIRST so Tasks 2 to 4 route through it from the start instead of retrofitting.

### Task 2: Relationship creation flow

- Create-attribute flow, type Relationship: two entity cards with the cardinality selector between them reading as a sentence; per-side associated-attribute name inputs with smart defaults; the sync banner as education; a symmetric toggle when both ends match, collapsing to one name input; cmd+enter submits.
- Machine code auto-generated from the names, editable under an Advanced disclosure; uniqueness validated per tenant.
- Submission calls `CreateRelationshipDefinition` (one transaction, 0 to 2 fields); the form never writes models directly.
- Lifecycle editing per the phase 3 spec, section 2.3: cardinality change allowed with keep-first confirmation when narrowing to a single side; entity-type ends locked after create; unpair and delete via the Plan 3.1 services.
- Tests: Livewire component tests for each cardinality, symmetric, the narrowing confirmation, and validation errors; browser click-through of the full flow.

### Task 3: Record chips and picker

- Chips with avatars and click-through; ordered chips with +N overflow, never a bare count.
- Picker: debounced instant search, avatars, keyboard navigation, inline create-new.
- Unlink on the chip; the one-to-one steal confirms inline before the writer resolves it.
- Provenance on hover from the ledger: actor and relative time (changed by X, 2d ago), read from the link row's created_by and active_from.
- All reads through `LinkReader` and the preloaded link relations; no N+1 on tables (assert query count in tests).
- Tests: Livewire interaction tests (search, select, reorder, unlink, steal confirm); browser click-through including empty state.

### Task 4: Field-management polish pass

- Searchable type-picker grid with icons and descriptions.
- Attribute table: reorder handles, type icons, badges, inline activate; relationship pairs visually connected across their two rows.
- Educational empty states; slide-over editing with cmd+enter; loading skeletons; full dark-mode audit.
- The stock record-configuration form Plan 3.2 shipped is replaced by the Task 2 flow: same services underneath, presentation only.
- Tests: table interaction tests; browser pass over every management screen.

### Task 5: Dual-flavor browser coverage in CI

- The critical browser paths (creation flow, chips and picker, attribute table) run in BOTH flavors in CI; the flavor comes from config so the same tests execute twice.
- A CI job matrix entry for `ui.flavor=native`; failures block merge like any other suite.
- Verify: both matrix legs green; screenshot evidence for polished light/dark/mobile attached to the PR.
