# Custom Fields 4.0, Plan 3.2: lookup_type Retirement

> **For agentic workers:** REQUIRED SUB-SKILL: sdd-lean, task-by-task. Runs on the `4.x` branch AFTER Plan 3.1 (substrate, including the record-links migration step). Phase 3 ends here: the package is fully on links with a stock-Filament record configuration, and phase 4 only restyles it. The substrate-independent housekeeping lives in Plan 1.1 and ran first. Spec: 2026-09-03-cf4-p3-relationships-substrate-spec.md. Every task ends with the package quality gate.

**Goal:** Remove the last traces of the old record storage: the `lookup_type` column, the settings keys it implied, and the code that only existed to serve json-array links.

**Ordering constraints (why this plan is last on the package side):**
- The column can only drop after `MigrateRecordLinksStep` (Plan 3.1, Task 12) has a definition for every record field; the step itself reads `lookup_type` to build them.
- The reflection helper dies here, not in Plan 1.1: its two callers (`RecordFilter`, `RecordSelectInputComponent`) are rewritten by Plan 3.1 Task 9 first.
- `FieldForm`'s record configuration is rebuilt here on definitions with stock Filament (Task 2); Plan 4.1 later replaces that stock form with the polished creation flow, a presentation change only.

### Task 1: Sweep every lookup_type consumer onto definitions

- The 18 referencing files (models `CustomField`/`CustomFieldSection`, `FieldSchema`, `RecordFilter`, `RecordColumn`, `RecordEntry`, `RecordSelectComponent`, `MultiChoiceEntry`, `ImportColumnConfigurator`, `ConfiguresBadgeColors`, `FieldForm`, `LookupResolver`, `LookupCache`, `LookupAttributeResolver`, `LookupPreloader`, `BackendVisibilityService`, upgrade steps) read the target entity type from the field's relationship definition instead.
- `requiresLookupType()` on `FieldSchema` becomes definition-driven.
- Verify: full suite; grep proves the only remaining `lookup_type` reads live inside `MigrateRecordLinksStep` (which translates the legacy column) and the drop migration.

### Task 2: Stock-Filament record configuration on definitions

- In `FieldForm` (`src/Filament/Management/Schemas/FieldForm.php`) the record type's configuration stops writing `lookup_type` and `allow_multiple`: it collects the target entity type, cardinality (`RelationshipCardinality` select), an optional paired-field name, and a symmetric toggle when both ends match, then submits through `CreateRelationshipDefinition` and its update sibling. Plain Filament components, no custom views; Plan 4.1 Task 2 replaces the presentation later on the same services.
- Editing an existing record field loads its definition; entity-type ends are locked after create (spec 2.3); narrowing cardinality to a single side asks the keep-first confirmation.
- Tests: Livewire tests creating a one-way and a paired record field through the management form, asserting a definition with 1 or 2 fields and no `lookup_type` write; an edit test asserting the ends are locked.

### Task 3: Drop the column, collapse the settings

- New publishable migration dropping `lookup_type` from custom_fields. Gate: `ValidateSchemaStep` fails while record-type values still live in json_value.
- `allow_multiple`/`max_values` are ignored for type record (cardinality owns this since Plan 3.1); remove their record-field surfaces from settings handling and the management form.
- Rename config key `selects.record_lookup` to match the record vocabulary.
- Verify: full suite; upgrade guide section updated with the column drop and the settings collapse.

### Task 4: Delete the reflection helper

- `Utils::invokeMethodByReflection` (`src/Support/Utils.php:65`) called Filament's private `applyGlobalSearchAttributeConstraints`; Plan 3.1 Task 9 rewrote both callers onto link queries.
- Confirm no caller survives, delete the helper. If any caller remains, replace with a public Filament API and fail loudly on absence.
- Verify: grep for `invokeMethodByReflection` returns nothing; record filter/search browser paths pass.
